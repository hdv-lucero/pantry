## Surface

**`SuggestionRun`** (new)
- `COVERAGE_THRESHOLD = Rational(2, 3)` — `Rational` on both sides of the comparison, so the boundary case (two of three items left → survives) is decided by exact arithmetic. See decision 2 for how much that actually buys.
- `enum :status, { queued: 0, running: 1, completed: 2, failed: 3 }` — default `queued` from the column default. Tested.
- `has_many :recipe_suggestions, -> { ordered }, dependent: :destroy`; `has_many :recipes, through:`. Destroying a run destroys its suggestions and leaves the recipes. Tested.
- `serialize :inventory_snapshot, coder: JSON` — no `type:`, so any JSON shape is legal; nothing reads it yet. Round-trip tested against a fixture.
- `.active` / `.archived` — on `archived_at`, not on status; a `failed` run is active. `.recent` — `created_at DESC`, not yet used by anything.
- `.archive_stale!(in_stock_names = PantryItem.in_stock_names)` — archives every active run below the threshold and **returns the runs it archived**. Tested with an explicit list and with the default.
- `#coverage(in_stock_names = …)` → `Rational`. **`1` when the run has no suggestions** (a queued run is never stale). Names not in the pantry at all count as out of stock. Tested.
- `#used_item_names` — `uses_items` across the run's suggestions, `uniq`, in suggestion order. Tested including the shared-item case.
- `#stale?(…)` — `coverage < COVERAGE_THRESHOLD`, i.e. strictly more than a third missing. Both sides of the boundary tested.
- `#archive!` — no-op if already archived, so the timestamp records the *first* drift. Tested under `travel 1.hour`.
- `#archived?` — `archived_at.present?`.

**`Recipe`** (new)
- `.normalize_url(url)` — returns `scheme://host[:port]/path` with query, fragment and trailing slash gone and the host downcased; **path case is preserved** (paths are case-sensitive), non-default ports are kept. Returns `nil` for `nil`, blank, unparseable strings, scheme-relative URLs, `javascript:`, and non-HTTP schemes such as `ftp:`. All of those tested.
- `normalizes :source_url, with: …` — so `where`/`find_by`/`find_or_create_by` normalize their argument too. Tested.
- `validates :source_url, presence: true, uniqueness: true` — a URL that normalizes to `nil` is invalid; the uniqueness validation turns a variant collision into `"has already been taken"` instead of a `RecordNotUnique`. Both tested.
- `.upsert_by_source_url(url, canonical_title:, source_name:)` — `find_or_create_by!`; the attributes apply **on create only**, so an existing row keeps its title, source and verdict. Tested both ways. Raises `RecordInvalid` on an unusable URL (tested).
- `.favorites` / `.blocked` — `make_again` true / false. A recipe never rated is in neither (tested).
- `#favorite?` / `#blocked?` — explicit `== true` / `== false`, because `nil` is a third state.
- `has_many :recipe_suggestions, dependent: :destroy`; `has_many :suggestion_runs, through:`.

**`RecipeSuggestion`** (new)
- `serialize :uses_items / :missing_items / :substitutions, coder: JSON, type: Array` — `type: Array` reads NULL back as `[]` and writes `[]` back out as NULL, so readers never see `nil` and the columns stay nullable. It also raises `SerializationTypeMismatch` **at assignment** on a non-array. Both tested.
- `validates :title, presence: true`; both `belongs_to` required. Tested.
- `.ordered` — `order(:position, :id)`; ties fall back to insertion order. Tested by reordering a fixture.
- `.cooked` / `#cooked?` — on `cooked_at`. Tested.

**`PantryItem`** (additions)
- `.in_stock` — `where("quantity > 0")`; a zero-quantity row is kept but is not an ingredient. Tested.
- `.in_stock_names` — `in_stock.distinct.pluck(:name)`; two rows of the same thing in different locations are one name. Tested.
- `#in_stock?` — `quantity.present? && quantity.positive?`. Asserted inside `"in_stock excludes anything at zero"`.
- `after_commit :archive_stale_suggestion_runs, on: %i[update destroy], if: :stock_left_the_pantry?` — fires on a destroy, or an update whose `quantity` changed to zero or below. Creates and quantity increases never run it. Five tests.

## Decisions a reviewer should weigh

### 1. One coverage score per run, over the union of the items its suggestions use

**The doc is ambiguous here.** §5: "a lightweight check recomputes a coverage score **for
each active run** — the fraction of **each suggestion's** `uses_items` still in stock". One
score per run, computed from per-suggestion lists — but no aggregation rule is given. Task 4
phrases it run-first: "given a run's suggestions and the live inventory, the fraction of
`uses_items` still in stock".

I implemented the run-level reading: `used_item_names` is the `uniq` union of every
suggestion's `uses_items`, and coverage is the fraction of *those* still in stock. So an item
three cards call for is one item that can go missing, not three.

The alternative is per-suggestion coverage averaged across the run, which weights items by
how many cards use them. The two agree on all five fixture runs; they diverge only when one
suggestion leans heavily on items another doesn't. I picked the union because it needs no
invented aggregation rule and because "more than a third of **used items** are out of stock"
reads as a fact about items, not about cards.

Covered by `"used_item_names counts an item two suggestions share only once"` plus the six
`coverage` tests.

**If a reviewer disagrees:** add `RecipeSuggestion#coverage(in_stock_names)` with the same
`Rational` arithmetic and make `SuggestionRun#coverage` the mean of it over
`recipe_suggestions`; `stale?`, `archive!`, `archive_stale!` and the trigger are unchanged.
The threshold constant keeps its meaning either way.

### 2. `Rational`, not a float, for coverage and the threshold

"More than a third out of stock" means a run with exactly two of three items left must
survive, so the comparison at `2/3` is load-bearing rather than incidental. `Rational` on
both sides makes it exact.

Honest about how much this buys: I checked, and `Rational(2, 3) < 2.0/3` is **false** in
Ruby — the nearest double sits just below two thirds — so a float threshold would have
landed the same way on this particular boundary. The argument for `Rational` is therefore
not a bug it fixes today; it is that the rule is a fraction, the data is a count over a
count, and exact arithmetic means nobody has to work out which way a binary fraction
rounded to know whether a run archives. The code comment says this; an earlier draft of it
claimed a float was outright wrong here, which was mistaken.

The cost: `run.coverage` returns a `Rational`, so any future UI has to call `.to_f` to
render a percentage. Locked by the two boundary tests (`Rational(2, 3)` → not stale,
`Rational(1, 3)` → stale).

### 3. `normalize_url` strips *all* query parameters, and one more thing than the doc names

§3's schema comment says "tracking params & fragments stripped"; the prose four paragraphs
later says "query params and fragments stripped, so tracking-parameter variants don't split
identity". Those aren't the same rule. I followed the prose — everything after `?` goes —
because an allowlist of tracking parameters is an empirical list that is never finished, and
because the task text also says "strip query params and fragments".

**Known limit, and it is a real one:** a site that identifies recipes by query string
(`/recipes?id=1234`) collapses every one of its recipes onto a single row. No such site is in
the fixtures, and Task 5's URL sanity checks are the natural place to reject those URLs, but
nothing currently detects it.

**Beyond the doc:** normalization also downcases the host and drops a trailing slash. Hosts
are case-insensitive and `/gyudon/` and `/gyudon` are the same page, so both serve the stated
purpose of not splitting identity — but neither is named in §3. Paths are *not* downcased,
since path case is significant. Non-default ports are kept. All tested.

**If a reviewer disagrees:** the whole rule is five lines in `Recipe.normalize_url`; dropping
the trailing-slash or host-downcasing clause is one line each, and the corresponding test
(`"normalize_url drops a trailing slash"`, `"normalize_url downcases the host but leaves the
path alone"`) goes with it.

### 4. The archiving trigger is a synchronous `after_commit` on `PantryItem`

§5 says "whenever inventory changes… a lightweight check recomputes", without saying where it
lives or whether it's a job. I hung it on `PantryItem` as an `after_commit` limited to the two
events the doc names — a destroy, or an update whose quantity hit zero — and it runs inline,
in the request.

Cost, stated plainly: `archive_stale!` loads every active run with its suggestions and does
the arithmetic in Ruby. For one user with a handful of active runs that is cheaper than any
bookkeeping that would keep a denormalized score honest, but it is O(active runs) per
zeroing write, and Task 6's cooking transaction will zero several items in one go and
therefore run the whole check once per item after the commit.

**Beyond the doc:** the guard is one `after_commit … on: %i[update destroy]` rather than the
`after_update_commit` / `after_destroy_commit` pair it reads as. Same-name commit callbacks
deduplicate in Active Support, so the pair silently kept only the destroy registration and the
zeroing test failed until it was collapsed into one. There is a comment on the line saying so.

I checked the mechanism rather than inferring it from the failure — subclassing `PantryItem`
in a throwaway `bin/rails runner` script and counting the chain (`_commit_callbacks.select { |c|
c.filter == :probe_check }`) gives **1** registration for a same-name pair and **2** for two
distinct method names. So two differently-named methods would also have worked; one
registration with an explicit `on:` is the version that can't be broken by a later rename.
That script is deleted too, and this is the one claim in this recap whose evidence a reviewer
has to recreate (four lines) rather than re-run.

**If a reviewer disagrees** (wants it in a job): `archive_stale_suggestion_runs` becomes
`ArchiveStaleSuggestionRunsJob.perform_later`, the five trigger tests wrap in
`perform_enqueued_jobs`, and CLAUDE.md's warning about the development queue adapter
(`:async` against a database with no `solid_queue` tables) becomes this task's problem instead
of Task 5's.

### 5. A rename can strand a run, and nothing notices

§5's trigger list is "item deleted or quantity hits zero", which is what I implemented.
But renaming "milk" to "whole milk" also removes `"milk"` from `in_stock_names`, and no
coverage check runs. The run stays active with a used item that no longer exists; the next
zeroing or deletion of *any* item picks it up.

Adding `saved_change_to_name?` to the guard would close it in one clause. I left it out
because the doc enumerates the triggers and because the exact-name echo rule makes a rename a
snapshot-invalidating event in general, not just a coverage one — worth deciding deliberately
rather than by reflex. No test asserts either behaviour.

### 6. `uniqueness: true` on `source_url`, on top of the unique index

§3 specifies only the index. The validation costs one `SELECT` per create — the same query
`find_or_create_by` already does on the upsert path — and buys a `"has already been taken"`
error instead of a `RecordNotUnique` exception for any writer that doesn't go through the
upsert. Tested (`"the unique index refuses a second row for the same normalized url"` —
the name says index, the assertion is on the validation).

**Race note:** `find_or_create_by!` is not atomic, so two concurrent upserts of one new URL
can still raise `RecordNotUnique` from the index. Single user, one suggestion job at a time,
and the task text names `find_or_create_by` explicitly, so I did not reach for
`create_or_find_by`. The index is what makes the failure loud rather than silent.

### 7. `favorites` / `blocked` scopes and the verdict predicates, added now

**Beyond the literal task text** — these are §5's preference lists and §4.3's favorites
badge, both consumed by Tasks 5 and 6, not by anything in Task 4. Four lines total, and
`Recipe` is where §5 says they live ("each a one-line query on the `recipes` table"). Tested.
Deleting them costs nothing if a reviewer wants them landed with their consumer.

### 8. Fixture design encodes the threshold

The three completed active runs use **4, 2 and 3** distinct pantry items — `beef_night`,
`breakfast`, `dessert` — chosen so that zeroing the single item `milk` puts them on three
different sides of the rule: unaffected, archived (1 of 2 left), and exactly-at-threshold
(2 of 3 left, survives). That is why the archiving tests can make one write and assert three
outcomes. `recipes(:gyudon)` is shared by `beef_night` and the archived `history` run so
cross-run identity (§3's whole reason for the table) has fixture coverage, and
`history_gyudon` uses `"bok choi"`, which no `pantry_items` fixture stocks, to cover the
never-in-the-pantry case.

Fixture files bypass callbacks, so `recipes.yml` URLs are written already-normalized and the
JSON columns are written as JSON strings — the same convention (and comment) Task 2 used for
normalized names in `pantry_items.yml`.

## What Task 5 inherits

- **`Recipe.upsert_by_source_url(url, canonical_title:, source_name:)` is the parser's write path.** Hand it the raw URL from the API response — `normalizes` does the normalization, so don't pre-normalize, and don't `Recipe.create`. It raises `RecordInvalid` if the URL doesn't survive normalization, which doubles as the last line of the URL sanity check §5 asks for (do the explicit checks first anyway; `normalize_url` only proves it's an http(s) URL with a host).
- **`PantryItem.in_stock_names` is the snapshot vocabulary.** The exact-name echo rule's validation compares against snapshot names; build the snapshot from these so the strings coverage measures against and the strings the model echoes are the same set.
- **`Recipe.blocked` and `Recipe.favorites`** are the two prompt lists, ready to serialize as title + source URL, and `Recipe.blocked` is also the parse-time filter's lookup.
- **Nothing archives a run on completion.** A run whose suggestions are parsed straight into a pantry that has already moved on stays active until the next inventory change; if Task 5 wants a coverage check right after parsing, call `SuggestionRun.archive_stale!` at the end of the job.
- **Coverage returns a `Rational`.** `to_f` before formatting.
- **Task 6's cooking transaction gets archiving for free**, via the `after_commit` on each zeroed `PantryItem` — but each zeroed item triggers a full `archive_stale!` pass, and each also broadcasts a refresh on `PantryItem::INVENTORY_STREAM` (Task 3). §4.3's "one click, three coordinated morphing updates" should fall out of the two mechanisms already in place; whether the repeated `archive_stale!` passes want batching is a Task 6 judgment call.
- **`SuggestionRun.archive_stale!` returns the runs it archived**, which is what a broadcast of "this run just archived itself" will want to iterate.

1. **Should a rename trigger the coverage check?** (decision 5) Due at Task 6, which is where §4.3's transaction makes item-level edits routine — and where the same question arises for whether a run's `inventory_snapshot` should be considered stale when names change under it.
2. **Union vs. per-suggestion-average coverage** (decision 1) — the fixtures can't distinguish them. Task 6 is the first place a reviewer will see coverage in the UI; if a per-card "this needs 2 of 3 things you no longer have" display shows up there, per-suggestion coverage lands with it and the aggregation question has to be answered for real.
3. **Does the threshold survive contact with a real pantry?** §5 says "initially: more than a third… tune from real use" and lists it as still-open. `COVERAGE_THRESHOLD` is one constant with two boundary tests pinned to `2/3`; changing it means changing those two tests' expected fractions.
4. **Where does the check run when it stops being cheap?** (decision 4) Deferring to a Solid Queue job is a one-line change, but CLAUDE.md notes the development queue adapter is unresolved until Task 5 — so Task 5 settling the dev queue is also what makes moving this into a job painless.
